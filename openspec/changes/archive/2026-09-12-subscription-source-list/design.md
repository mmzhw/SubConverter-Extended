## Context

`url=` 是 subconverter 的订阅源参数。它的子语法有两层分隔：

```
url=<源1>|<源2>|...            多源用竖线
url=<前缀选项>,<源URL>         单个源的前缀选项用逗号
```

也就是说逗号是**源内部**的分隔符，不是源之间的。用户按直觉用逗号分隔多源时，
整串会变成一个 URL（实测 `url:` 字段原样包含逗号），客户端取不回来。

前端现状：

- `url-builder.ts:39` — `params.set('url', state.sourceUrl)`，原样写出
- `url-parser.ts:18` — `url.searchParams.get('url')`，原样读入
- `useFormState.validateSource()` — `new URL(state.sourceUrl)` + 协议判断

`new URL('https://a/x,https://b/y')` **不抛错**（逗号在路径中是合法字符），
所以误用形态能通过校验，问题被静默带到最后一步。

## Goals / Non-Goals

**Goals:**

- 多订阅源在界面上一行一个、可读可改。
- 生成的 `url=` 一律用 `|` 连接，与后端既有实现一致。
- 导入含 `|` 的链接再生成能往返一致。
- 逗号误用给出可操作提示，而不是静默产出坏链接。

**Non-Goals:**

- 不改后端、不改 `url=` 语法。
- 不自动"纠正"用户的历史逗号链接（可能改变语义，且逗号在源前缀里有正当含义）。
- 不在本次引入"源前缀选项"的图形化编辑（界面本就未支持）。

## Decisions

### D1: 规范形用换行，wire 形用 `|`，在边界处转换

- `state.sourceUrl` = 换行分隔（文本域内容即状态，所见即所得）
- `buildSubUrl`：换行 → `|`
- `parseSubUrl`：`|` → 换行

备选：状态里直接存 `|`。否决 —— 那样文本域里会出现竖线，用户编辑时容易误删或误加，
且换行才是"一行一个"的自然表示。

### D2: 只在**两个**边界转换，中间层不感知

`splitSourceUrls` / `joinSourceUrls` 两个纯函数放在 `lib/source-urls.ts`，
`url-builder` 与 `url-parser` 各调一次。组件不重复实现分割逻辑。

### D3: 逐行校验，并单独识别"逗号误用"

`validateSource` 改为对每一行做 `new URL()` + http/https 判断。

额外：当某一行里出现 `,http://` 或 `,https://`，判为**逗号误用**并给出专门文案
（"检测到用逗号分隔多个订阅源；请一行一个"）。

为什么不直接按逗号拆分：`interval:21600,https://…` 这类**源前缀**含逗号，
无条件拆分会把前缀截断。实测该形态在现有界面**本就被判非法**（`new URL()` 对
`interval:21600,https://…` 得到 `interval:` 协议），所以专门文案不会新增误报，
只是把"看起来像 URL 却不行"换成可操作的解释。

### D4: 换行与空行容错

文本域里允许空行与行首尾空白；空行丢弃，各行 trim。因此从别处粘贴带空行的列表
不会产生空源（空源会让 `url=` 出现 `||`，后端会取到空 URL）。

### D5: 往返一致性由纯函数单测保证

`joinSourceUrls(splitSourceUrls(x)) === x`（对规范化后的 x），
以及 `wire → state → wire` 的稳定。这是本次最容易回归的点（用户会导入旧链接再生成）。

## Risks / Trade-offs

- [历史逗号链接] → 不静默改写，改为给出提示；用户改一次即可。
- [源前缀用户] → 现有界面本就不支持（校验即拒绝），本次不使其更差；专门文案会
  指出问题所在。
- [文本域高度] → 单源时也显示文本域会占更多竖向空间；用较小的 `rows`（3）并允许
  拉伸，单源用户视觉成本可接受。
- [与短链/预设的往返] → `parseSubUrl` 的改动会影响导入路径，需覆盖单测。

## Migration Plan

- 无数据迁移：wire format 不变，既有链接照常解析。
- 单源用户行为完全不变。
- 发布：纯前端改动，随镜像重建即可。
